ModelSphere · 插件体系

插件可移植性架构

插件产物固定，宿主契约固定；平台实现各自演进。北极星这类插件最终应当同一个包同时装进 ModelSphere 和 Global，差别只在谁来安装、谁来填环境参数。

日期 2026-11-16 范围 plugin.yaml v1 · Plugin CRD · 插件前端 bundle 结论 契约层已成型，机制层还缺两处收敛
01两个问题

先回答最初的两个问题

现阶段插件格式和 Global 完全通用吗？

不是整个包通用，而是契约层通用。SDK 注册、共享宿主、IAM 路由、i18n 模型来自 Global；manifest 的承载方式、安装器、bundle 供给地址是我们自己的。旧 Global 格式的包不用再考虑，还没发布。

未来能不能把北极星直接装到 Global？

能，但前提是把「机制层」定死、平台层各做各的适配。装不进去的从来不是插件业务代码，而是插件对宿主的三处隐含依赖：能力查询的路径、business.console 这个复合名字、以及能力声明放在哪一侧。这三处收敛之后，同一个 tgz 在两边只是安装器不同。

02三层模型

平台、机制、插件

分成三层看，要求就很清楚：平台层可以完全不同，机制层必须一致，插件层只依赖机制层。

平台 A · 当前 ModelSphere Console
React + Vite 自研 shell，Plugin CRD modelsphere.dev/v1alpha1，cmd/modelsphere 安装器，bundle 从已装 release 供给。
平台 B · 目标 Rise Global
Next.js，自有一套插件管理体系与投递方式。这些差异不需要消除。
各自实现 · 不要求一致
机制层 · 唯一必须固定的部分 宿主契约
SDK 全局对象与注册调用 · 共享模块的 window 别名 · API 路由声明（IAM ReverseProxy）· manifest 字段 · i18n 注册 · 菜单 key 约定 · 能力提供（provides）与绑定（consumes）· 同一个 bundle 供给方式
插件只认识这一层
插件层 · 产物固定 一个 tgz
Helm chart + plugin.yaml + frontend/<entry>。不含任何平台的构建步骤，业务代码里不出现平台内部包名。

ModelSphere 与 Global 的框架选择、CRD 与管理体系、安装命令，全部落在平台层。它们可以各自演进，不构成插件复用的障碍。

03能力模型

能力不是注入，是声明与绑定

requires: { swiss: true } 这种写法有两个问题。布尔位只说明「我需要一样东西」，不说明从哪来、谁保证、哪个版本；而且这几个名字是安装器里写死的枚举，第三方提供方没法扩展，两个提供方用了同一个名字也没法区分。

方向也是反的。imagePullSecrets 和 inferenceNamespaces 由平台提供，swiss 的网关地址和代理 key 由 swiss 插件提供。北极星能用它们，是因为提供方公开声明了自己提供这些数据、声明的版本在哪，使用方再按声明去绑定。

# swiss 插件：提供方声明
provides:
  - capability: swiss.modelsphere.dev/gateway
    version: v1
    values:
      endpoint: .endpoint
      apiKeyRef: .apiKey.secretRef
# 北极星：使用方声明
consumes:
  - capability: swiss.modelsphere.dev/gateway
    version: v1
    from: { kind: Plugin, name: swiss, version: ">=0.3.0 <0.5.0" }
  - capability: platform.modelsphere.dev/image-pull-secrets
    version: v1
  - capability: platform.modelsphere.dev/inference-namespaces
    version: v1

能力标识是反域名加路径，提供方身份和版本都在名字里，同名不会撞。要锁到某个具体提供方实例、或者限制它的插件版本范围时，才用 from 补上 kind 和 name。

安装器只做解析：在已安装的提供方里找匹配的能力和版本，把结果写进使用方的 values。写进去的键按提供方限定，两个提供方同名也不会串：

# 安装器写给北极星的 values（片段）
consumed:
  modelsphere.dev/swiss:
    endpoint: http://swiss-gateway.inference:8080
    apiKeyRef: swiss-proxy-key
  modelsphere.dev/platform:
    imagePullSecrets: [rise-registry]
    inferenceNamespaces: [swiss-deploy]
角色负责声明什么安装时核对什么
提供方
含平台自身		 能力名、版本、输出哪些键 它确实能渲染出这些键
使用方 绑定哪项能力、能力版本；需要时用 from 锁定提供方实例与版本 绑定是否可解析
安装器 不写名称 缺提供方、版本不匹配、有多个提供方但未指定，一律预检失败

平台不需要特殊处理。平台就是提供方 platform，它的能力随平台版本一起声明。这样三个布尔位全部消失，插件包也不再假设任何平台的 values 长什么样。

三个直接后果

  • 同名不再冲突：能力标识带提供方域名，解析结果也按提供方隔离。
  • 第三方能扩展：新提供方只要声明 capability 和版本，已有使用方不用改安装器代码。
  • 依赖关系变成显式的：北极星绑定 swiss 的能力，就说明 swiss 必须先装、且版本落在区间里；缺了在预检就报，不会装完才炸。

它和插件可移植性的关系

提供方声明属于机制层，平台只是众多提供方中的一个。换平台时插件包一行不改，变的只是新平台声明了哪些能力、用哪个版本号。真正稳定的不是「宿主注入三样东西」，而是「谁能声明、怎么绑定、怎么解析」这套规则。

04插件产物

什么算「产物固定」

判定标准只有一个：同一个 tgz 不重新构建，能在两个平台装起来并跑通。要达到这个标准，插件的运行时依赖面必须只剩机制层暴露的接口。

  • 包结构固定：chart 内 Chart.yaml + plugin.yaml + frontend/<entry>，由平台负责解包和供给。
  • manifest 字段固定：apiVersion: v1、name/group/version/displayName、provides / consumes、frontend{type, runtime, entry}。字段内容固定，存在 CRD 里还是 Global 的管理体系里，是平台的事。
  • bundle 只从宿主全局对象取依赖：React、UI 组件、Router、Query 都不打包进插件，编译期改写成宿主注入的全局对象。
  • API 走声明式路由：通过 iam.theriseunion.io/v1alpha1 的 ReverseProxy 声明 /api/ 前缀，平台负责鉴权和转发。
  • 文案走宿主 i18n：通过 SDK 注册到宿主实例，不自己另起一套语言切换。

bundle 的依赖实际去了哪里

插件 SDK 的构建脚本已经把这件事做掉了。源码里写 @modelsphere/ui，编译后并不带这个包的代码，而是从宿主的全局对象上取同名导出：

插件源码 import编译后从宿主取提供方
reactwindow.__MODELSPHERE_SDK__.React宿主 React
@modelsphere/ui…SDK__.ui宿主 UI 包
react-router…SDK__.business.console.Router宿主 Router 单例
@tanstack/react-query…SDK__.business.console.Query宿主 QueryClient 单例
@modelsphere/plugin-sdk打包进 bundle（契约代码），运行时读全局对象插件自身

注意第一列的写法不是问题，第二列才是契约。全局对象同时挂了三个名字：

window.__MODELSPHERE_SDK__
window.__GLOBAL_SDK__      // 同一个对象
window.__RISE_SDK__        // 同一个对象

这就是「同一个 bundle 两边都能跑」的技术基础。真正需要冻结的是第二列的接口形状，也就是机制层。

05现状与差距

已经固定的，和还差一点的

项状态说明
SDK 注册与共享宿主 已固定 迁自 rise-global-extension 4.2.1，注册与共享宿主契约保持兼容
三个 window 别名 已固定 Global / Rise / ModelSphere 三个名字指向同一个对象
i18n 模型 已固定 同一个 rise-locale 存储键与 locale 集合，语言选择可迁移
API 路由声明 已固定 iam.theriseunion.io/v1alpha1 ReverseProxy + authProxy: true，IAM 原生能力
能力声明 待收敛 现在是三个布尔位 requires；应换成提供方的 provides 与使用方的 consumes，按提供方和版本解析
能力查询 待收敛 插件现在调 /api/capabilities 这个 Console 端点；应改为 SDK 方法，让各平台各自实现
business.console 待收敛 名字里带 Console；契约里应收敛为中性的宿主命名空间，或由 Global 提供同名 shim
manifest 承载 平台侧 ModelSphere 存 CRD，Global 存自己的管理体系；字段一致即可
安装与卸载 平台侧 各平台各写一个安装器，负责读 consumes、从已声明能力的提供方解析绑定并填值
bundle 供给地址 平台侧 ModelSphere 是 /plugins/<cr-name>/<entry>，Global 用自己的投递方式

剩余的未知

本仓库里查不到 Global 当前的 manifest 结构与前端投递方式，因此上面「机制层已成型」的判断，依据的是我们这边已迁入的契约与构建产物，不是 Global 的现行实现。要把「还差两处收敛」变成一份确定的改动清单，需要一份 Global 正在使用的插件包，或 Global 加载插件的那段代码。

结论

插件是可移植的资产，平台是可替换的实现。把机制层冻在 SDK、ReverseProxy 和 manifest 字段上，北极星换平台时只需要换安装器，不需要动插件。

范围说明：上一轮讨论中旧 Global 格式的包（modelsphere.io/v1alpha1）已按「未发布、面向未来」的结论排除，本文不包含兼容该格式的内容。安装链路、CRD、前端 import 说明符的差异归为平台层，也不在本轮收敛目标内。
