Architecture · Plugin Runtime

ModelSphere 可插拔架构

插件是一个 Helm Chart，注册是一条 Plugin CR，Console 只观察这两样东西。下面按数据流把这条链路讲完：包怎么定义、CLI 做什么、CR 怎么被校验、前端怎么加载、后端怎么鉴权。

分支 imneov/polaris-global-plugin-runtime CRD modelsphere.dev/v1alpha1 SDK @modelsphere/plugin-sdk 1.0.1 更新 2026-11-17
01 / Package 插件包

Chart + plugin.yaml + frontend/。安装的唯一输入。

02 / Release Helm release

Deployment、Service、PVC、ReverseProxy 在集群里真实存在的运行时。

03 / Registration Plugin CR

一条集群范围内的声明：谁已安装、该不该被 Console 加载。

§ 01

三个平面，一个观察者

插件系统把「装」和「认」拆成两件事。CLI 负责把包变成 Helm release；Plugin CR 负责告诉 Console「这个 release 可以对外暴露」。两件事之间没有隐含触发，所以 CR 可以由人 kubectl apply，也可以由 GitOps 审批后写入。

Console 在这条链路里是被动的：它 watch CR，再回读对应的 release，把 plugin.yaml 和 frontend/ 挂出来。它不装插件，不升级插件，也不改插件 release 里的任何资源。

设计后果 安装权与发布权可以分开授予：平台工程师执行 plugin install，业务方只提交一条 CR。因为 Console 从不推断「装了就该显示」，禁用插件只需要删 CR 或给它打上禁用标记，release 原样留着。
§ 02

包格式：两个元数据文件，一个前端入口

包必须同时是合法 Chart 和合法插件。Chart.yaml 给 Helm 看，plugin.yaml 给 Console 看，两边都要能独立读通。

canary/
├── Chart.yaml          # name / version / type
├── plugin.yaml         # 身份、入口、能力声明
├── values.yaml
├── templates/          # Deployment、Service、ReverseProxy…
│   └── reverseproxy.yaml
└── frontend/
    ├── index.umd.js    # frontend.entry 必须指向它
    └── candidates.json # Tailwind 候选类清单，宿主统一编译

下面是一个真实清单（Canary，0.4.0）。它声明了三项能力，但一个值也没写——值由安装时从提供方解析出来：

name: canary
group: modelsphere.dev
apiVersion: v1
version: 0.4.0
displayName: Canary
description: Persistent model inference experiments.
consumes:
  - capability: platform.modelsphere.dev/image-pull-secrets
    version: v1
  - capability: platform.modelsphere.dev/inference-namespaces
    version: v1
  - capability: swiss.modelsphere.dev/gateway
    version: v1
frontend:
  type: component
  runtime: remote
  entry: index.umd.js
activation:
  policy: auto
校验点规则在哪里被执行
apiVersion只接受 v1，其余版本直接拒绝CLI · Console
name / group与 CR 的身份一致，并可反推出 group--name 资源名CLI · Console
version严格 SemVer，且必须等于 Chart.yaml 的 versionCLI · Console
frontendtype: component、runtime: remote、entry 必须是包里真实存在的文件CLI · Console
provides / consumes能力名是 <group>/<name>，版本是合法版本形态CLI
同一份文件，读两次 CLI 在安装前校验一次，Console 在每次 reconcile 时从已安装 Chart 的 Files 里再解析一次。所以包被替换、版本对不上、入口缺失，都会在 Console 侧表现为 CR 进入 Degraded，而不是页面上一个 404。
§ 03

CLI 的六个动词

CLI 是最窄的一层：它只做「包 → 集群对象」的转换，不替 Console 做决定。

命令做什么明确不做
plugin validate读包的结构与两个元数据文件，检查入口文件存在不连集群
plugin packagehelm package 的封装，产出 .tgz不改元数据、不注入版本
plugin install校验 → 解析 consumes → 写临时 values → helm upgrade --install --atomic --wait不创建 CR，不改 Console values
plugin registration从包与集群参数生成 CR，输出到 stdout不执行 kubectl apply
plugin list列出已部署的 Helm release，并指出哪些有 CR不改任何状态
plugin uninstall要求 CR 存在 → 删 CR → helm uninstall不动没有注册的 release

--atomic --wait 是刻意的：安装超时会让 release 回滚，而不是留下一个 pending 的 release 把下一次升级卡住。uninstall 以 CR 为前置条件，是为了避免「CR 还在、release 已经没了」这种半边状态——那种状态下 Console 会一直重试读取并停在 Degraded。

唯一的非常规实现是 list 的发现方式。Helm 把一个 release 的全部内容（打包后的 chart 与 values）存在一个 Secret 里，单个通常上百 KB；集群级 list 很容易到数 MB。CLI 因此用 client-go 的 metadata client 只取 PartialObjectMetadata，按 500 条分页，靠 Secret 上的 label 还原 release：

// 只要元数据，不要 Secret 正文
selector := "owner=helm,status=deployed"
lister := metadata.NewForConfig(config).Resource(secrets)
for {
    page, _ := lister.List(ctx, metav1.ListOptions{
        LabelSelector: selector,
        Limit:         500,
        Continue:      cursor,
    })
    // name / status / namespace 都来自 label 与 metadata
    cursor = page.GetContinue()
    if cursor == "" { break }
}
这条不是优化，是可用性 同一个查询用 kubectl get secrets -A 在慢链路上会被传输层截断并报 stream ID 1; INTERNAL_ERROR；只取元数据后同样的查询从数 MB 降到几十 KB。凡是「列出集群里有什么」的地方，都不应该去拉对象正文。
§ 04

能力：提供方声明，消费方只写需求

插件不应该知道宿主怎么配置镜像拉取密钥、推理命名空间或模型网关。它只声明「我需要什么能力」，具体的值在安装时解析，写进一份临时 values 文件交给 Helm。

提供方有两类。内置的两个由 Console 安装时确定：

内置能力提供什么典型键
modelsphere.dev/platform镜像拉取密钥（同命名空间）、可部署推理的命名空间imagePullSecrets、inferenceNamespaces
modelsphere.dev/swiss模型网关地址与密钥引用endpoint、apiKeyRef、apiKeyKey

第三类提供方是已安装的插件：它可以在 provides 里声明自己的能力，之后注册的插件就能消费它，并且覆盖同名的内置能力。解析顺序固定为「已注册插件优先，内置兜底」。

解析结果写进 consumed.<provider group>/<name>.<key>，文件权限 0600，安装结束即删除。插件拿到的是 Secret 的引用，不是 Secret 的值——这份 values 里没有明文密钥。

解析失败发生在 Helm 之前

情况结果
没有任何已安装提供方no installed provider offers capability …
有提供方，但不满足 from 指定capability … is not available: installed providers offer …
多个提供方竞争且没写 fromoffered by multiple providers …; pin one with from
版本不满足 SemVer 区间capability … is not available: …
同命名空间能力装在别的命名空间namespace-scoped to "…"; install this plugin in "…"
提供方声明的键后面没有值… publishes no value at … for "…"
为什么要求显式 from 两个提供方同时满足时，选谁都是猜。让安装失败并要求写 from，比让插件静默连到错误的网关好。同样，消费方不能靠自带的 consumed 默认值扩大作用域——CLI 会把解析结果覆盖在上面。
§ 05

Plugin CR：身份与状态

CRD 是 modelsphere.dev/v1alpha1，资源名必须是单个 DNS-1123 段，所以 group 与 name 用 -- 拼起来：

modelsphere.dev/canary      → 资源名 canary
modelsphere.dev/my-app      → 资源名 my-app
// 冲突或非法字符用 x- + base32 转义，解析时反向校验

spec 是人写的，status 只有 Console 写。两者的差异就是排障入口。status.phase 描述的是当前这一代（generation）的加载结果：

Phase含义此时 UI 上能看到吗
Pending刚被观察，尚未读取 release否
Installing / Upgradingrelease 正在变化视上一代结果而定
Installed校验通过，已进入注册表是
Degradedrelease 在，但加载失败；conditions 写原因否
Failed / Uninstalling不可用，或正在摘除否
最常见的 Degraded Console 需要读 Helm 的 release Secret。它的 Role 只覆盖自己所在的命名空间；插件装在别的命名空间时，那边必须额外授权同样的 Secret 读取权限，否则 CR 会稳定停在 Degraded，而 release 本身完全正常。
§ 06

Console 注册表：只观察，不推断

注册表由一个动态 informer 驱动（30 秒重同步），变更进入限速工作队列，每个对象单独 reconcile。首次全量 reconcile 完成后才把注册表标记为 ready——在那之前 /readyz 返回 503，这样滚动更新时流量不会打到一个「看起来起来了、实际还没有插件」的实例上。

每次 reconcile 做四件事：

步骤行为
摘除CR 被禁用或正在删除 → 从注册表移除，不碰 release
读取校验身份、scope: helm、type: helm，读 release Secret 的 .Last()
校验release 必须是 deployed；chart 名与版本要和 CR 一致；plugin.yaml 严格解析；frontend/entry 必须存在
登记写入条目：前端文件、入口、ReverseProxy 路由；随后 UpdateStatus 写回 Installed 或 Degraded

ReverseProxy 规则在这里被收紧：路径必须以 /api/ 开头、以 / 结尾、且 authProxy: true；上游只接受 http/https 与合法端口。不满足的规则整条丢弃并让 CR 进入 Degraded，而不是挂一个不带认证的路径上去。

§ 07

前端分发与 SDK 契约

宿主只暴露一张清单和一个静态目录。/plugins/index.json 的每一条就是一次挂载声明：

{
  "id": "canary",
  "group": "modelsphere.dev",
  "version": "0.4.0",
  "entry": "/plugins/canary/index.umd.js",
  "styles": [],
  "backend": {
    "name": "canary",
    "prefix": "/api/canary",
    "writePermission": "canary.write"
  }
}

文件从 release 的 Chart Files 里按 frontend/ 前缀取，逐个走 ValidPluginAsset 校验（合法相对路径，不含 \ ? # % :），响应固定 Cache-Control: no-store。入口是单个 UMD 文件，样式先于入口加载。

运行时依赖由宿主提供单实例：React、react-router、@tanstack/react-query、@modelsphere/ui 都从宿主注入，插件不打包副本。SDK 声明 VERSION 1.0.1，加载前比对主版本，不匹配就拒绝——这比让一个老插件在新宿主上静默崩溃容易排查。

插件通过 createPlugin 注册菜单、路由、组件、数据源、可见性规则、展示形态和动作。任一环节抛错，已注册的部分回滚，条目整体不生效。

前端是公开的 除 /api/ 与 /oauth/ 之外，所有路径都不需要登录——插件 JS 被当作受信代码直接下发。因此包里不能出现任何密钥、令牌或内部地址；插件需要的凭据一律通过能力解析以 Secret 引用的方式进入后端。
§ 08

两条并行路径与一次鉴权

浏览器侧只有两条路径，它们共用同一套认证中间件，但授权点不同。

静态路径 /plugins/*

  1. 拉 /plugins/index.json
  2. 按 entry 取 UMD 文件与样式
  3. SDK 注册菜单、路由、组件
  4. 失败则整条回滚，菜单不出现

接口路径 /api/<plugin>/*

  1. 认证中间件解析出用户与用户组
  2. 匹配已注册路由的最长前缀
  3. 按方法映射动词并校验 backends
  4. 反代到 Service，注入 X-Remote-*

REST 方法被映射成 RBAC 动词，而不是笼统的「读写」：GET/HEAD/OPTIONS → get，POST → create，PUT/PATCH → update，DELETE → delete。授权对象是 backends，资源名就是插件名：

# 只读访问 canary 的后端
verbs: ["get"]
resources: ["backends"]
resourceNames: ["canary"]

# 写访问另外需要
resourceNames: ["canary.write"]

writePermission 会随 index 一起下发，IAM 界面据此显示可授予的权限项。反代时把调用者身份写进 X-Remote-User / X-Remote-Group，与 Rise Global apiserver 对 ReverseProxy 的约定一致——同一个后端不用为两种入口写两套身份解析。

为什么强制 authProxy 如果允许挂一条不带认证的 ReverseProxy，插件就能绕过 Console 的鉴权直接把内部服务暴露出去。把它做成加载时的硬性条件，让这个错误无法通过配置发布出去。
§ 09

一次完整安装

把前面的部件串起来，顺序是这样的：

  1. validate — 读包，确认 Chart、plugin.yaml、前端入口三者自洽。
  2. install — 解析 consumes，写 0600 临时 values，helm upgrade --install --atomic --wait，结束后删除临时文件。
  3. wait — release 进入 deployed；Deployment、Service、ReverseProxy 就位。
  4. registration — 生成 CR YAML 到 stdout。
  5. apply — 人或 GitOps 把 CR 写进集群。
  6. reconcile — Console 收到 CR，回读 release，校验通过后写入注册表，status.phase: Installed。
  7. load — 浏览器取 index.json 与 UMD，SDK 注册菜单与路由。
  8. call — 插件请求 /api/<name>/*，认证、backends 鉴权、反代到 Service。
  9. uninstall — 删 CR（插件立即从 UI 消失），再 helm uninstall。

出现问题时先看哪里

现象先确认
plugin list 为空安装只建 release；CR 是否存在才是列表的依据
Console 启动即 503CRD 是否安装；informer 是否已完成首次 reconcile
CR 一直 Degradedstatus.conditions；常见为 release 不存在、chart 版本不匹配、Secret 读权限缺失
菜单不出现/plugins/index.json 里有没有该条目
插件 JS 404entry 是否在 frontend/ 中，路径是否被资产校验拒绝
接口 403角色在 backends 上是否对插件名授予了对应动词
扩展点 增加一个插件不需要改 Console 代码：它只是多一个 Chart、多一条 CR、多一个 UMD 入口。Console 侧唯一会变的是注册表里的条目数，以及合并后的 Tailwind 候选类集合。
